## Fixes

### Signup session handover and OTP submission

In the app (Capacitor APK), the verified session was not always handed to the app's session layer. Profile and session requests could then reach the backend with no authorization token. The verified session is now handed over explicitly, and the code is submitted once, so duplicate OTP submissions no longer happen. (`51816ac`)

### Adopted session dropped after signup

Calling `signOut({ scope: 'local' })` after adopting the session could invalidate the provider session that had just been adopted. It is replaced with in-memory state cleanup, so the session stays alive. The welcome email is now sent reliably after account setup. (`beeac10`)

### Profile created before the session that references it

The backend tried to create a session before making sure the app profile existed. For accounts where verification succeeded but profile creation had failed earlier, this caused foreign-key failures. The order is now: profile sync → validation → session creation → notification. Login notifications are no longer sent before a session exists. (`b0755c2`)

### Session cookies shared between environments

Development and production used the same session cookie names under `.meetifyy.app`, so one environment could overwrite or reuse the other's session. Each environment now has its own cookie names, and production keeps its existing names. (`89e33e6`) Stale host-only cookies from older deployments could also override the newer domain cookies. They are now expired whenever a session is issued or cleared. (`70cf95d`)

### CORS open across environments

The broad `https://*.meetifyy.app` pattern is replaced with explicit origins per environment:

- Development and production frontend and admin origins are separate.
- Credentialed requests can no longer cross environments.
- Unsafe origin patterns are rejected at validation.
- The Capacitor app origin is included.

(`e1f13a2`)

### Stale CSP hashes

CSP hashes were generated before the final prerendered HTML existed, so they went stale. Now:

- Inline scripts stay the same between builds.
- The build ID lives in a separate `meetifyy-build` meta tag.
- Hashes are checked after prerender, on every page, and a wrong or missing hash fails the build.
- Cloudflare's JavaScript Detection script is still handled separately, because it is injected at the edge.

(`3f58667`)

### Settings back button looping on phones

The mobile Settings back button pushed parent routes instead of following history, so it could loop. It now goes back when history exists, falls back to the right parent for deep-linked pages, and uses replace navigation where needed. The desktop split view is unchanged. (`f376741`)

### Untyped catch bindings and function parameters

Every catch binding was `any`, so `${err.message}` compiled even when the thrown value was not an `Error`. A string or plain object printed "undefined", and a thrown `null` threw again inside the catch and lost the original failure. `useUnknownInCatchVariables` and `strictFunctionTypes` are now on, and `errorMessage()` and `errorStack()` give the message of an `Error` and a serialisation of anything else. The duplicate-notification check now narrows to `PrismaClientKnownRequestError` before reading `.code`. (`a6eda13`)

### Untyped request and token claims

- **Guards:** The rate-limit guards, `OptionalJwtGuard`, `VerificationGuard`, `DevEndpointGuard` and `@CurrentUser` read an untyped request, so the identity they key on was `any` from the start. A `GuardRequest` type now describes the request as a global guard sees it, with the body as `unknown`. `@CurrentUser('x')` only accepts a key of `AuthenticatedUser`. Rate-limit keys are unchanged. (`6e58186`)
- **JWT validation:** `validateToken` returned `Promise<any>`, so the object every authorization decision reads was untyped. It now returns `AuthenticatedUser | null` built from a narrowed payload. A correctly signed token whose subject is not a string, such as `sub: 42`, used to produce a user with a numeric id that no row could match. It is now refused like a token with no subject. Signature, algorithm allowlist and issuer checks are unchanged and still run before any claim is read. (`6bf48ac`)
- **Admin tokens:** The pending, access and refresh tokens were read as `any`, so a refresh token missing a claim sent `undefined` into `crypto.update()`, which threw a TypeError and returned a 500 instead of a 401. Each claim is now read from a narrowed payload and a missing one is refused before any lookup. OTP and TOTP verification share one check that a pending token was issued for the step it is used at. (`f3a73e3`)

## Improvements

### Landing page light and dark mode

The landing page forced light mode and fought the global theme system. It now follows the selected or system theme, including themed scrollbars, the signup journey components and the footer. (`15fe5a5`)

### Dark-mode phone surfaces

The remaining full-screen phone surfaces are pure black in dark mode: post view, Settings, drawers, chat settings, and the gallery and group-settings screens. They use the `--color-surface-screen` token instead of scattered overrides. (`330e328`)

### Branding

- The reload loader screen is updated, and the transparent Meetifyy logo now matches the mobile APK splash. (`f29e7de`)

## Findings

### Backend lint audit

The backend had 8,000+ lint errors. They were grouped by rule and root cause, not auto-fixed or suppressed. The plan:

- Fix recurring patterns at their source, and separate mechanical issues from real type-safety or correctness problems.
- Avoid new `eslint-disable` comments.
- Write down coding rules that stop the patterns coming back.
- Add tests where a finding shows a real runtime risk.

The first fixes landed late in the day (see Build & Tooling and the type-safety fixes above). The lint backlog is now tracked in a ledger that can only shrink.

### Untested auth paths

`validateToken` was stubbed in every existing spec, and `AdminJwtGuard` and the admin token paths had no spec at all. Real-token specs now cover subject precedence, a forged key, an expired token, the remote fallback, and `peekUserId` never calling out. For admin auth they cover a valid session, a token without a session id, a forged token, CSRF on mutations, an OTP-step token at the TOTP step and a refresh token without its key. (`6bf48ac`, `f3a73e3`)

## Build & Tooling

- **Lint scope:** `eslint .` ran out of heap because it linted `dist/`, where every compiled file is outside `tsconfig.json` and the type-aware parser built a separate program for each. `dist`, `coverage`, `uploads` and scratch are now ignored. The 14 email templates (`.tsx`) were never linted, and the scripts had no tsconfig. Both are now covered through `tsconfig.tooling.json`, and the lint scripts run with a 4 GB heap. (`7671aeb`)
- **Stricter rules:** `no-explicit-any`, `no-floating-promises` and `no-unsafe-argument` are errors, and so are unused disable directives. The `any` is now reported where it is written instead of as dozens of violations in its callers. (`7671aeb`)
- **Seed script removed:** `prisma/seed.ts` and `ALLOW_DESTRUCTIVE_SEED`, its only reader, are gone. It no longer compiled against the schema. (`7671aeb`)
- **Mechanical fixes:** Prettier formatting (243), redundant type assertions (25) and one stale `eslint-disable` across 28 files. Every changed file transpiles to the same JavaScript, and all ten email templates render byte-identical HTML. (`327f4df`)
- **Blocking CI lint:** The ESLint step ran with `continue-on-error`, and the backlog grew from about 4.6k to about 7k `no-unsafe-*` findings. It now blocks. The 9,377 existing violations are recorded in `eslint-suppressions.json`, so only new ones fail, and ESLint also fails when a recorded violation is fixed but the ledger is not pruned. CI also type-checks the specs and scripts, which the build tsconfig excludes. (`9f34b1b`)
